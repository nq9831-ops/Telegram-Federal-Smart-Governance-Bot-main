# Telegram Federal Smart Governance Bot 产品与 Web 管理后台建议

> 本文整理项目当前阶段的功能规划、交互细节、Web 管理后台设计和实施优先级。
>
> 适用项目：`nq9831-ops/Telegram-Federal-Smart-Governance-Bot-main`
>
> 核心目标：让每一次自动治理都能**解释、追踪、申诉、回滚**，并确保重复投递不会造成重复处罚或二次伤害。

---

## 1. 产品定位与总体原则

项目已经具备审核、信用分、联邦治理、群组收录、商家管理和审批后台等基础能力。下一阶段不建议继续无边界增加模块，而应优先完善自动治理的运营闭环：

```text
消息 / 事件
  → 审核判定
  → 案件编号
  → 自动处置
  → 信用分流水
  → 通知
  → 人工复核 / 申诉
  → 反向动作
  → 完整审计
```

### 核心设计原则

1. **可解释**：用户和运营者知道为什么被处理。
2. **可追踪**：能够从案件追到消息、规���、处罚、信用分和通知。
3. **可申诉**：误判有明确申诉入口和处理状态。
4. **可回滚**：推翻处罚时能够执行解封、回滚信用分等反向动作。
5. **幂等**：Webhook 重试、联邦重复广播和任务重跑不能造成重复处罚。
6. **最小权限**：高风险操作需要明确授权、二次确认和审计。
7. **渐进启用**：新规则先观察，再执行；新模块默认安全关闭。
8. **隐私最小化**：不存储不必要的消息正文，不在后台默认暴露明文身份信息。

## 2. 用户侧 Bot 功能建议

### 2.1 基础命令

建议优先补充以下命令：

| 命令 | 作用 |
|---|---|
| `/start` | 私聊入口、隐私说明、功能引导 |
| `/help` | 按角色分类显示可用命令 |
| `/status` | 查看当前群治理状态 |
| `/my_score` | 查看自己的信用分和当前状态 |
| `/score_history` | 查看信用分变动记录 |
| `/score_explain` | 解释最近一次分数变化 |
| `/appeal <案件编号> <理由>` | 针对指定案件提交申诉 |

`/help` 不建议一次展示全部命令，应按角色分类：

```text
基础功能
群组管理
审核与申诉
信用分
收录与商家
隐私与数据
```

`/status` 建议显示：

```text
治理状态：已启用
治理模式：观察 / 执行
审核规则：12 条
违禁词：34 条
反刷屏：已开启
入群验证：关闭
AI 审核：关闭
待复核案件：5 条
```

### 2.2 审核结果反馈

被删除、禁言或封禁时，建议向用户发送简短、可解释的通知：

```text
你的消息已被系统处理。

处理类型：删除消息
规则类别：广告/诈骗风险
处罚结果：禁言 10 分钟
案件编号：#A-20260919-00128

如认为判断有误，请联系群管理员或提交申诉。
```

通知可以包含规则类别、风险等级和案件编号，但不要暴露：

- 完整命中词；
- 完整正则表达式；
- 第三方 AI 的内部提示词或评分细节；
- 其他用户的身份信息。

### 2.3 申诉闭环

建议将申诉设计为明确状态机：

```text
PENDING
  ↓
UNDER_REVIEW
  ├─ APPROVED       维持原处理
  ├─ REJECTED       推翻原处理并执行反向动作
  └─ NEED_MORE_INFO 需要补充材料
```

每个案件至少保存：

- 案件编号；
- 当事人和关联群组；
- 原处理类型；
- 申诉理由；
- 提交时间；
- 当前状态；
- 处理人和处理时间；
- 处理意见；
- 是否执行反向动作。

### 2.4 观察模式

建议将群组治理拆成三种模式：

```text
OFF       关闭自动治理
MONITOR   只记录，不处罚
ENFORCE   正式执行处罚
```

新规则和新群组默认进入 `MONITOR`，经过观察期并确认误报率后再进入 `ENFORCE`。

建议增加：

```text
/preview_rule <规则>
/rule_test <规则> <示例文本>
/monitor on
/monitor off
```

测试结果示例：

```text
测试结果：
命中规则：SCAM_AIRDROP
风险等级：MEDIUM
建议动作：进入人工复核
实际动作：仅记录，不删除
```

## 3. 审核、处罚和信用分细节

### 3.1 统一审核结果模型

不同审核层最终应输出统一结构：

```text
riskLevel
ruleId
category
confidence
recommendedAction
needsReview
hardLine
explanationCode
```

推荐处理链路：

```text
审核层 → ModerationVerdict → PolicyResolver → Enforcement
```

审核模块不应直接各自操作 Telegram，避免重复删除、重复禁言或不同模块互相覆盖结果。

### 3.2 风险和动作分离

不要将风险等级和处罚动作硬编码绑定为：

```text
HIGH = BAN
```

更合理的结构是：

```text
风险等级：HIGH
建议动作：删除 + 人工复核
当前群策略：删除 + 禁言 1 小时
```

群组可以配置：

```text
低风险：记录
中风险：删除
高风险：删除 + 禁言
硬红线：删除 + 冻结 + 必须复核
```

### 3.3 统一信用分流水

不能只保存最终分数，必须保存不可变的分数事件：

```text
score_before
score_delta
score_after
source_type
source_id
idempotency_key
reason
operator_id
created_at
```

建议对 `idempotency_key` 增加唯一索引。推荐构成：

```text
event_type + source_id + user_id
```

这样可以防止同一消息重试、重复联邦广播或任务重跑导致重复扣分。

### 3.4 信用分恢复规则

恢复规则应公开且固定，例如：

- 30 天无违规，恢复 5 分；
- 完成一次教学任务，恢复 2 分；
- 复核推翻时完整回滚原扣分；
- 联邦处罚不能由普通群管理员直接恢复；
- 达到指定分数后自动解除观察状态。

管理员不应直接编辑总分。人工调整应创建“信用分调整事件”，填写理由并写入审计日志。

### 3.5 豁免机制

可以支持：

- 用户豁免；
- 群组豁免；
- 消息类型豁免；
- 规则豁免；
- 有效期豁免。

每条豁免必须记录创建人、原因、过期时间、影响规则和是否跳过硬红线。普通豁免不应绕过硬红线。

## 4. Web 管理后台总体设计

建议将现有审批中心发展为“治理运营工作台”，采用左侧导航、顶部状态栏和主内容区：

```text
┌──────────────────────────────────────────────┐
│ 当前节点 │ 系统状态 │ 待处理数 │ 操作员 │ 退出 │
├──────────┬───────────────────────────────────┤
│ 总览     │                                   │
│ 审核中心 │             主内容区               │
│ 群组管理 │                                   │
│ 规则管理 │                                   │
│ 信用管理 │                                   │
│ 联邦治理 │                                   │
│ 商家管理 │                                   │
│ 通知中心 │                                   │
│ 审计日志 │                                   │
│ 系统设置 │                                   │
└──────────┴───────────────────────────────────┘
```

未实现的模块应明确标注“即将支持”，不要进入空白页面。

### 4.1 首页总览

顶部统计卡片建议包括：

```text
待处理案件       今日新增案件       已超时案件       硬红线待复核
      12              86                3                1
```

系统状态区显示：

- 应用状态；
- Telegram 连接；
- 数据库连接；
- 最近任务执行时间；
- 最近失败任务数；
- 待重试外部动作数。

首页中部放“优先处理队列”，默认按以下顺序排序：

1. 硬红线；
2. 已超时；
3. 高风险；
4. 等待时间长；
5. 普通风险。

底部可以放三个初始图表：

- 最近 24 小时审核量；
- 各风险级别占比；
- 维持与推翻比例。

### 4.2 审批中心列表

建议支持：

```text
状态：待处理 / 已维持 / 已推翻
风险：NONE / LOW / MEDIUM / HIGH / HARD_LINE
群组
案件来源
时间范围
是否超时
处理人
```

默认列：

- 案件编号；
- 风险等级；
- 规则分类；
- 群组；
- 匿名用户标识；
- 自动处理动作；
- 创建时间；
- 等待时长；
- 是否超时；
- 当前状态。

默认不要展示明文 Telegram User ID，建议显示类似：

```text
用户 A7F3...91C2
```

只有经过授权的操作员才可以展开更多身份信息。

### 4.3 案件详情页

详情页建议分为四部分：

#### 案件摘要

```text
案件 #1024
状态：待复核
风险：HIGH
原处置：删除消息 + 禁言 1 小时
创建时间：2026-09-19 12:20
```

#### 判定信息

```text
规则类别：诈骗
规则编号：SCAM_AIRDROP
审核层：L1 / 违禁词
是否硬红线：否
是否需要人工复核：是
```

#### 自动动作

```text
12:20 消息已删除
12:20 用户已禁言
12:20 信用分 -15
12:21 案件进入复核队列
```

#### 审计时间线

```text
12:20 系统创建案件
12:20 执行删除
12:20 执行禁言
12:21 通知复核人
13:05 操作员打开案件
```

### 4.4 裁决操作

建议按钮明确区分：

```text
[维持处罚] [推翻并解封] [需要更多信息]
```

“推翻并解封”必须二次确认，确认内容应明确影响：

```text
确认推翻此案件？

此操作将：
1. 将案件标记为 REJECTED；
2. 尝试解封相关用户；
3. 回滚本次信用分扣减；
4. 记录你的操作和理由。
```

按钮文案应使用“确认推翻并解封”，不���只写“确定”。推翻处罚、修改信用分、解封、删除规则、修改联邦节点和结算保证金时，理由必须填写。

### 4.5 操作影响预览

执行高风险操作前，先显示：

```text
本次操作预计影响：

案件状态：PENDING → REJECTED
用户状态：MUTED → ACTIVE
信用分：72 → 87
Telegram 动作：尝试解封
通知对象：1 名用户、2 名复核人
```

业务状态和 Telegram 外部动作可能暂时不一致，界面必须分别显示：

```text
业务裁决：成功
外部动作：待重试
```

## 6. 权限、登录和安全体验

当前共享 Token + `X-Operator-Id` 方式可作为第一版，但界面应明确显示：

```text
当前登录方式：运营 Token
当前操作员：operator-123
```

短期建议：

- Token 不显示明文；
- 自动过期；
- 退出时清理 `localStorage`；
- 401 自动回到登录页；
- 403 区分“无权限”和“凭据无效”；
- 切换操作员时清除旧状态；
- 高风险操作再次确认操作员身份。

长期建议改为真正的运营者账号体系：

```text
账号 / SSO
角色
权限
登录会话
MFA
操作员审计
```

共享 Token 不能充分证明实际操作者身份，不适合长期多人运营。

## 7. 前端交互规范

### 7.1 状态颜色

```text
绿色：正常 / 已处理 / 已恢复
蓝色：信息 / 观察中
黄色：待处理 / 临近超时
橙色：高风险 / 需要关注
红色：硬红线 / 失败 / 外部动作未完成
灰色：关闭 / 已归档
```

不能只依赖颜色，必须同时显示文字或图标。

### 7.2 时间显示

同时显示绝对时间和相对时间：

```text
2026-09-19 20:20:31
5 分钟前
```

顶部显示当前系统时区，避免免打扰时段和 SLA 产生误解。

### 7.3 空状态

```text
暂无待复核案件
当前筛选条件下没有结果，或所有案件已经处理完成。
[清除筛选]
```

### 7.4 加载和失败

每个页面都应支持：

- 首次加载骨架屏；
- 操作中禁用按钮；
- 防止重复提交；
- 失败后保留用户输入；
- 重试按钮；
- 请求关联 ID；
- 明确区分业务成功和外部动作失败。

### 7.5 列表分页和输入安全

`/words`、`/rules`、`/review_list`、`/listing_list` 和后台表格都必须分页，不要一次加载全部数据。

用户输入必须：

- 正确转义 HTML 和 Markdown；
- 防止伪造机器人消息格式；
- 限制长度；
- 对正则表达式做编译和灾难性回溯检查；
- 对排序字段使用白名单。

## 8. 联邦治理和外部动作的保护

联邦广播、跨群封禁和处罚令属于高风险功能，必须具备：

1. 节点身份、公钥、状态和撤销管理；
2. 处罚令有效期和序列号；
3. 防重放检查；
4. 入站签名校验；
5. 节点撤销后的拒绝策略；
6. 处罚撤销广播；
7. 节点间状态不一致检测；
8. 外部 API 失败后的重试和死信记录。

任何会产生 Telegram 外部动作的操作都应显示执行状态：

```text
业务操作：成功
Telegram 操作：成功 / 失败 / 待重试
```

不能因为外部 API 超时，就让操作员重复点击导致重复处罚。

## 11. 验收标准

每个高风险功能至少应满足：

- 正常流程可用；
- 重复请求不会重复执行；
- 权限不足时拒绝；
- 业务失败时有明确错误；
- 外部动作失败时可重试；
- 所有操作都有审计记录；
- 误判可以申诉；
- 推翻后可以执行反向动作；
- 不在前端默认暴露敏感身份信息；
- 单元测试覆盖确认、取消、重复提交和失败分支；
- 页面具备加载、空数据、错误和权限不足状态。

## 12. 最终建议

项目 Web 后台最重要的不是页面数量，而是让运营者能够快速回答四个问题：

1. **发生了什么？**
2. **系统为什么这么处理？**
3. **现在需要我做什么？**
4. **我点击之后会造成什么后果？**

因此，最推荐的下一步是：

> **总览首页 + 审批中心时间线 + 裁决影响预览 + 规则测试页 + 审计日志页。**

这五项对实际运营价值最高，也最能降低误操作、误封和重复处罚风险。
